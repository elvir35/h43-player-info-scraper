# Phase 5 security review

2026-11-11. Scope: local administration implementation, shared editorial/public projection, image flow and configuration tooling. **No Phase 5 staging deployment or real Access login has occurred.** This is an evidence-based implementation review and automated test record, not a claim of complete production security.

## Trust boundaries and controls

| Boundary / threat | Implemented mitigation |
| --- | --- |
| Browser -> Access -> admin Worker: forged identity, expired/wrong application token | `admin-auth.ts` verifies RS256 via fixed configured Cloudflare JWKS, issuer, audience, required subject/email/time/type; bounded JWT size; explicit D1 allowlist and enabled flag; first-login subject pin; service/unknown identities rejected. Email headers are ignored. |
| Static routing / alternate hostname bypass | Admin assets always run the authenticated Worker first. Exact ADMIN_ORIGIN is enforced. No private admin route is forwarded by the public Worker. No `ctx.access` assumption behind Static Assets or Service Bindings. Unconfigured authentication/secrets fail closed. |
| Authenticated coach -> another team / escalation | Every content/read/preview/upload/publish/history/image request checks current team/partition ownership. Role and assignments live in D1, not browser state. Mutations recheck current authority in conditional SQL; coach role grants no global team access. Admin-only role/assignment/settings routes; self-lockout prevention. |
| Cookie session -> CSRF | Every mutation requires exact Origin, same-origin fetch metadata where present and a constant-time-checked HMAC token bound to verified user/JWT session/origin. No permissive admin CORS, unsupported methods rejected, no browser-held account or R2 secrets. |
| Untrusted content -> browser XSS | Strict exact content schema/bounds, NFC/plain text, HTML/control-character rejection, exact HTTPS Instagram/TikTok profile validation, email validation. UI and preview use text nodes; no HTML editor or arbitrary embeds. Self-only admin script/style/connect/frame CSP, no-store, nosniff, no-referrer and same-origin resource policy. |
| Concurrent editors / replay / partial publishing | Optimistic draft/permission versions and expected published head; conditional SQL rechecks active partition/role/image state. Revision, pointer/version and audit are a transactional D1 batch. Failed batch rolls back all writes. Rollback creates a fresh owned revision. |
| Upload -> private R2 / path or object-reference attacks | Generated UUID keys, no filenames/paths supplied by user, team/partition metadata, authenticated same-team image reads. JPEG-only streamed 2 MiB server input, full strict decode with memory/pixel limits, stripped-metadata re-encode and bounded output. Browser conversion is convenience, not trusted validation. SVG/invalid/oversized data rejected. |
| Private image -> public delivery | No public R2 endpoint. Coaches with current team publishing access can publish ready team-owned images without a separate photo approval. Descriptions are optional; the widget supplies a team-specific alternative when omitted. Public image GET joins the exact current published revision/image/team/partition; no-store. Unpublished/retired/cross-team/missing objects return no image. |
| Cleanup -> a newly referenced image | Claim only old unreferenced objects; state changes to deleting before R2 removal. Draft and publish SQL only accept ready images. Historical revision references are retained. Pending uploads are tracked before R2 writes, so failed finalization remains private and eligible for cleanup. |
| Local/test -> staging/production | Loopback-only synthetic harness is separate from bundled Workers; fixtures use example.test identities. Templates disable admin by default; generated staging config requires verified Access app, exact staging origin, private R2, dedicated staging DB and unique limiter. No CI deploy, remote migration or hardcoded secret. |

The public Worker only exposes published DTOs/media and maintains its existing read-only route boundary. Scraping code and source authority are unchanged.

## Authentication and secrets

Access should use explicit approved emails with OTP or an approved IdP, protecting the entire admin hostname. The configured AUD must belong to this staging application; production has a separate one. Cloudflare's complete signed assertion is verified locally; `Cf-Access-Authenticated-User-Email` and caller roles are not trusted. JWKS uses a fixed issuer-derived HTTPS location, RS256 allowlist, timeout and bounded cache; unknown key/expiry/audience/configuration returns safe denial. Permissions are read from D1 on every request and rechecked on writes. Disabling a user removes access without waiting for browser session expiry.

`CSRF_SECRET` is generated securely per environment, stored only as a Cloudflare secret, and never included in public vars/config/assets. Its token is HMAC bound to actor subject/email, verified JWT iat/exp and admin origin. Secret rotation invalidates old CSRF tokens; reload obtains a current token after Access verification. Ingestion credentials remain separate and unchanged. Account deployment permissions must be scoped to reviewed Worker/D1/R2/Access operations and never placed in the portal.

Expired JWTs return 401. A real Access login redirect is handled as an expired session using manual redirect handling; unsaved controls remain available to copy before reload. Network errors do not silently publish. After an uncertain publish acknowledgment, reload history rather than assuming the write failed; expected versions guard retries.

## Database and audit

All request values use bound D1 statements. Team/partition/revision/image ownership is checked, and public responses never expose draft JSON, actor emails, access subjects, object keys or audit records. Roles cannot be submitted through content JSON. First verified subject binding, draft saves, image reservation/finalization, publication/rollback and permission/settings actions are audited. Logs contain request IDs/status/component/method only; tokens, payloads and names are not logged. Immutable publication history supplies actual previous content, publisher and time. Global user/role administration requires current admin authority; there is no arbitrary SQL endpoint.

Admin and public Workers are trusted account-level principals sharing only their environment's dedicated D1/R2. R2 bindings do not provide application-level read-only capability; the public Worker code implements GET-only media, while the admin Worker performs controlled writes. Restrict who can change either trusted Worker or administer storage. Separate production resources/identities and private backups are required.

## Freshness and retention

Drafts/previews/admin responses/public aggregate/media responses are no-store. Publishing flips a primary D1 pointer atomically, so no new editorial cache needs purging. The existing bounded schedule cache is unrelated. Already rendered content cannot be remotely erased; reload immediately or wait for the five-minute visible-widget refresh. Publishing a revision without the image hides its URL and causes subsequent old-image requests to return 404. Client copies/downloads cannot be recalled.

Unused uploads become cleanup-eligible after seven days and are processed in bounded daily batches, including interrupted pending uploads. Draft/history references prevent deletion; failed R2 deletions retain metadata for retry. Assign an operator to monitor failures/backlog. Wider revision/audit/backups retention awaits club approval; no destructive history purge has been scheduled. Account-side R2 public access must remain disabled.

## Remaining risks / deployment gates

1. **High — infrastructure verification:** current OAuth Access/R2 reads returned 403. Real organization/app/IdP policies, private bucket, resource/account scopes and actual Access login/logout/expiry must be verified by an authorized operator. h43lund.se was absent from this login's zone inventory; no custom domain was assumed or changed.
2. **High — approval and photo permissions:** the Phase 5 brief explicitly requires staging approval after local tests. No Phase 5 remote deployment/migration/bootstrap is performed. Initial administrator/P11 coach data is privately prepared from the user's explicit instructions. Photo permission defaults false; player-name permission is not image permission. Production requires separate approval and isolated resources.
3. **Medium — image processing cost/limits:** full JPEG decode/re-encode is CPU-bound. The proposed 1,000ms paid-plan limit and real representative image timing/memory tests need account-side verification. Do not assume Workers Free supports this flow. Codec/Workers/JWT packages need ongoing advisories/updates; local limits reduce but cannot eliminate parser risk. No new image-processing service was enabled.
4. **Medium — trusted editors/source:** authorized publishers can publish misleading text or wrongly attest photo rights; software cannot verify real-world permissions. An account/Worker compromise is inside the trust boundary. Use least privilege, subject pin/reset procedures, revocation, content history and audit review.
5. **Medium — operations/retention:** establish monitoring for Access failures, publish errors, storage failures, CPU overruns, cleanup backlog and backups. Current existing six-hour roster workflow is still not enabled. Privacy/retention ownership and production restore drills remain open.

## Roster-detail trust boundaries — 2026-11-13

SportAdmin remains authoritative for membership and names. Public row IDs are untrusted technical input, bounded/validated and scoped by team/source/category. Server-created UUID membership keys survive only continuous exact source-ID/name matches; departures, rejoining and renames invalidate associations. No display-name or fuzzy matching is used. These identifiers are private and not authorization credentials.

Roster metadata uses existing team-scoped JWT/CSRF permissions, strict field validation, prepared queries and versioned editorial saves. Cross-team/unknown/incorrect-category keys reject. Newly changed metadata saves atomically require the roster observation version checked during validation. Publication merges optional values only into currently valid members, preventing stale revisions from reintroducing removed members or their details. Editorial responsibilities cannot grant coach/admin access. Source-ID additions and optional metadata do not require a new D1 schema. Retain the updated backend during an asset rollback because older strict ingestion readers do not understand the extended private records. Public responses/DOM expose no raw source IDs or membership keys.

## Optional player portraits — 2026-11-13

The user explicitly requested optional player photos, superseding the initial names-only/no-portraits product scope. Reuse the authenticated JPEG upload, native Images metadata-stripping WebP normalization, private R2 and existing team publishing authority. No new service, database migration or mandatory photo-approval/description gate is introduced. Coaches remain responsible for choosing photos permitted for publication.

RosterDetail adds an optional imageId, defaulting to null for old content. New and changed portrait references require current player membership; leader attachments reject. Conditional draft and publication SQL rechecks every referenced image as ready and owned by the same team/season. This prevents foreign, orphan/deleting or unready references from being attached during a cleanup race. X-H43-Roster-Images: 1 advertises updated editor support; older cached editors cannot save over a draft containing portraits without refreshing. This header is a compatibility check, not authentication.

Public image GET allows the exact currently published hero or a published portrait attached to a currently active player key in the matching team/source/season, with roster publication authorized. A roster departure, identity change or published removal/replacement revokes the portrait reference without cache delay. URLs remain no-store/nosniff and serve only sanitized ready objects. Private previews use authenticated team image endpoints. Failed processing leaves the previous draft/public image unchanged.

Cleanup protects portrait references in drafts and revision history before claiming old unreferenced objects. Removed portraits can remain privately retained by history, consistent with existing team-photo retention; they are not made public by retention. If an image is intentionally referenced by another active portrait or the published hero, that other reference still authorizes its URL.

Keep both portrait-aware backend Workers during a UI rollback. Older editorial validators do not understand imageId, and older cleanup code does not protect portrait references. Revert public embed assets alone to hide photos safely; any backend downgrade requires a reviewed data/reference conversion. Production remains a separate approval gate.
